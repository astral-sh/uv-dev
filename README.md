# Prevent older uv versions from downgrading the lockfile revision

Issue: astral-sh/uv#22911

Classification: bug (mixed-version lockfile metadata loss; requested write policy requires design)

## Summary

The reported behavior is reproducible. A lockfile generated by uv 0.13.5 at revision 5 was rewritten by uv 0.8.15 at revision 3 after changing only the project's version. The older writer exited successfully without warning about the revision downgrade. With `pyproject.toml` absent, uv 0.13.5 then failed on `uv sync --frozen` with the exact reported error. A separate fixture confirmed that the rewrite removes recorded `default-groups` metadata as well.

The downgrade is conditional: an unchanged-project `uv lock` with uv 0.8.15 preserved the revision-5 lockfile byte for byte. Frozen sync with the manifest present also accepted the downgraded revision-3 lockfile. The quoted error concerns discovery without the workspace manifest, rather than all frozen sync operations.

The reporter supplies Windows 11 and uv 0.13.5, but no Python version, older writer version, project configuration, or complete command sequence. Reproduction used Linux x86_64, CPython 3.12.3, the installed uv 0.13.5, and an official uv 0.8.15 executable. This establishes the behavior with a concrete older writer; it does not identify the reporter's exact writer or reproduce Windows specifically.

## Classification

Retain the bug classification for the demonstrated loss of metadata and resulting loss of manifest-free frozen-sync capability. The requested refusal to overwrite a newer revision, and any `--force` override, remain policy/design decisions. Reproduction does not establish that accepting a newer revision is itself incorrect: `docs/concepts/resolution.md` explicitly defines revision changes as backward compatible and readable by older uv versions. Reading compatibility and preservation when rewriting are separate concerns.

There is no demonstrated regression specifically introduced by uv 0.13.5 and no supplied last known-good version. The relevant changes added revision-5 metadata and manifest-free discovery in uv 0.12.22 and 0.12.23 respectively. No matching downgrade-prevention fix was identified in the related-issue research. A future change cannot alter already distributed older executables.

## Reproduction

**Outcome: reproducible.**

### Environment and fixture

- Platform: Linux x86_64; CPython 3.12.3 at `/usr/bin/python3`.
- New writer and frozen-sync reader: `uv 0.13.5 (x86_64-unknown-linux-gnu)`, installed on `PATH` at `/opt/hostedtoolcache/uv/0.13.5/x86_64/uv`.
- Older writer: uv 0.8.15, extracted into the temporary directory from its official PyPI manylinux x86_64 wheel after verifying the wheel's published SHA-256. Historical source at that tag defines lockfile `REVISION = 3`.
- All projects, environments, downloads, and caches were under `/tmp/uv-22911-v7f7pbxi`. Commands used an isolated subprocess environment and temporary XDG/cache paths. Python downloads were disabled. The main reproduction ran offline with `--no-config`.
- Single virtual project, no dependencies, no workspace members, no explicit groups or sources. No package builds or registry access were needed for locking or syncing.

Initial `pyproject.toml`:

```toml
[project]
name = "revision-repro"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = []
```

### Commands and observations

The following is the command sequence, with `uv` resolving to the installed 0.13.5 and `uv_old` pointing to `/tmp/uv-22911-v7f7pbxi/downloads/uv-0.8.15`. Run it in a temporary project containing the manifest above, with temporary cache/config/data paths. The recorded subprocesses set `UV_OFFLINE=true`, `UV_PYTHON=/usr/bin/python3`, and `UV_PYTHON_DOWNLOADS=never`.

```sh
uv --no-config lock
# exit 0; writes revision = 5

mv pyproject.toml pyproject.saved
uv --no-config sync --frozen
# exit 0; warns that discovery without pyproject.toml is experimental
mv pyproject.saved pyproject.toml

"$uv_old" --no-config lock
# exit 0; unchanged manifest preserves the lockfile byte for byte
```

Change only `[project].version` from `"0.1.0"` to `"0.2.0"`, then run:

```sh
"$uv_old" --no-config lock
# exit 0; rewrites revision = 5 to revision = 3

uv --no-config sync --frozen
# exit 0 while pyproject.toml is present

mv pyproject.toml pyproject.saved
uv --no-config sync --frozen
# exit 2 with the reported error
```

The old writer's complete stderr for the rewrite was:

```text
Resolved 1 package in 1ms
Updated revision-repro v0.1.0 -> v0.2.0
```

The lockfile changed only its revision and the project package's version:

```diff
 version = 1
-revision = 5
+revision = 3
 requires-python = ">=3.12"

 [[package]]
 name = "revision-repro"
-version = "0.1.0"
+version = "0.2.0"
 source = { virtual = "." }
```

The subsequent manifest-free sync emitted:

```text
error: Frozen lockfile discovery requires a lockfile with revision 5 or later; run `uv lock` to update it
```

Restoring `pyproject.toml` and running uv 0.13.5 `lock --refresh --no-index` restored revision 5. Removing the manifest again and running `sync --frozen --offline` then succeeded. `UV_OFFLINE` was unset for the refresh command because refresh and offline mode conflict; `--no-index` sufficed for this dependency-free fixture.

### Metadata-loss variant and version requirement

A separate single-project fixture added:

```toml
[dependency-groups]
docs = []

[tool.uv]
default-groups = ["docs"]
```

With normal project configuration enabled, uv 0.13.5 `lock --offline` wrote `default-groups = ["docs"]` in the project's lockfile package entry. After changing the project's version, uv 0.8.15 `lock --offline` both downgraded revision 5 to 3 and removed that entry. The empty `docs` group metadata remained; the configured default-group selection did not.

After restoring the lockfile with uv 0.13.5, adding `required-version = ">=0.12.23"` under `[tool.uv]` and changing the project version again caused uv 0.8.15 `lock --offline` to exit 2 without changing the lockfile:

```text
error: Required uv version `>=0.12.23` does not match the running version `0.8.15`. Update `uv` by running `uv self update`.
```

uv 0.13.5 accepted the same configuration and updated the project successfully. This mitigation check used normal configuration discovery, without `--no-config`.

### Evidence and limits

Command stdout, stderr, exit codes, and before/after lockfiles are retained in `/tmp/uv-22911-v7f7pbxi/evidence/`. The original older writer and its re-resolution trigger remain unknown. The minimal reproduction uses a project-version change; it does not show that every no-op `uv lock` downgrades a lockfile. Windows was not tested. More workspace/group variants are unnecessary to establish this behavior because both the downgrade and the exact downstream error occurred without a workspace or dependencies.

## Mitigation

Set an appropriate minimum uv version using `[tool.uv].required-version` in the source project's `pyproject.toml`. The tested minimum `>=0.12.23` includes revision-5 metadata and manifest-free frozen sync. Regenerate a downgraded lockfile with a compatible uv using `uv lock --refresh` while the manifest is present. Use normal configuration discovery so the version requirement is enforced.

The error's suggestion to run `uv lock` requires restoring or providing the project manifest; a lockfile alone does not contain the source project's full configuration for re-resolution.
